# Accessible Forms with useId

## What Was Built
`<label>` elements linked to their inputs via `htmlFor`/`id` were added to `AddTransactionForm` and `AddAccountModal`, with IDs generated by React 18's `useId` hook to guarantee uniqueness per component instance.

## File Location
`src/components/AddTransactionForm.tsx`, `src/components/AddAccountModal.tsx`

---

## Concepts Introduced

### useId — collision-safe IDs for reusable components

**Plain English**
Every `<label>` in HTML needs to be linked to its `<input>` using a matching pair: `htmlFor` on the label and `id` on the input. The problem in React is that components can render multiple times on the same page — if you hardcode `id="description"`, two forms would have two elements sharing the same ID, and clicking either label would be unpredictable. You can't generate IDs with `Math.random()` because you'd get a new value on every render, breaking the link. `useId` solves this: it gives you a string that is stable across renders and unique per component instance. The two copies of `AddTransactionForm` get different IDs automatically.

**Technically Speaking**
`useId()` is a React 18 hook that returns a string like `":r0:"`, `":r1:"`, etc. The IDs are assigned sequentially per React root and are stable across renders — the same component instance always gets the same ID. Crucially, `useId` is aware of React's server-side rendering (SSR) model: it generates IDs deterministically based on the component's position in the component tree, so the ID produced during SSR matches the ID produced during client-side hydration. This eliminates the hydration mismatch bug that occurs when IDs are generated with a random or counter approach.

The recommended pattern is one `useId()` call per component instance, with field-specific IDs derived as template literal suffixes: `const formId = useId(); const nameId = \`\${formId}-name\``. This keeps the hook call count minimal and produces readable IDs.

**Vue / Laravel Analogy**
Vue 3.5 added a `useId()` composable that works identically:
```ts
// Vue 3.5+
const id = useId()
const nameId = `${id}-name`
```
In older Vue code, the common workaround was a module-level counter:
```ts
let uid = 0
const fieldId = `field-${uid++}`
```
This works for client-only apps but fails with SSR — the server generates IDs in a different order than the client, causing hydration mismatches. In Laravel Blade, IDs are either hardcoded (fine for server-rendered forms that never appear twice) or generated with `\Str::uuid()` in the controller and passed to the view. The problem is client-specific — no hydration means no mismatch.

**Common Mistakes**
1. **Using `crypto.randomUUID()` or `Math.random()` for IDs.** These generate new values on every render, meaning the `id` changes every time state updates. The `htmlFor`/`id` link breaks momentarily and screen readers can lose track of associations.
2. **Calling `useId()` once per field instead of once per component.** You can call `useId()` multiple times, but the pattern of one call + suffixes (`${formId}-name`, `${formId}-type`) is cleaner and generates fewer hook registrations.
3. **Displaying `useId` values to users.** The generated strings (`":r0:"`) contain colons which are valid in HTML `id` attributes but unusual. They're intentionally collision-resistant, not human-readable. Never use them as visible text.

### htmlFor / id — the label-input contract

**Plain English**
A `<label>` element on its own is just styled text. What makes it useful is the link to its input: when you click the label, the browser focuses the input. When a screen reader reads the form, it announces the label text when the input is focused. This link is made by giving the input an `id` and giving the label a `htmlFor` attribute with the same value. Without this link, the label is decorative only — clicking it does nothing, and screen readers can't associate the label with the field.

**Technically Speaking**
`htmlFor` is React's JSX name for the HTML attribute `for` (which is a reserved word in JavaScript, hence the rename). The browser maintains a bi-directional association: the label's `for` attribute points to the input's `id`, and `HTMLLabelElement.control` exposes the associated input programmatically. Clicking the label fires a click event on the associated control. The ARIA spec requires that interactive form controls have an accessible name — `<label>` with `htmlFor` is the preferred way to supply it. Without it, screen readers fall back to `placeholder`, `aria-label`, or `aria-labelledby`.

**Vue / Laravel Analogy**
In Vue and plain HTML, the attribute is `for` (not `htmlFor`):
```html
<label for="name">Account name</label>
<input id="name" type="text" />
```
In JSX, `for` is renamed to `htmlFor` because `for` is a reserved JavaScript keyword — `for (let i...)`. The behavior is identical; only the attribute name differs between HTML and JSX.

**Common Mistakes**
1. **Using `placeholder` as a substitute for a label.** Placeholder text disappears when the user types, leaving the field unlabeled during input. It also has lower contrast than label text and isn't announced reliably by screen readers.
2. **Wrapping the input inside the label instead of using `htmlFor`.** Implicit labels (`<label>Input name <input /></label>`) work in browsers but have inconsistent screen reader support. The explicit `htmlFor`/`id` pattern is universally supported.
3. **Mismatched `htmlFor` and `id` values.** A typo means the label click does nothing. TypeScript won't catch this — the values are plain strings. Using `useId` and derived suffixes eliminates typo risk since both sides reference the same variable.

## Code Walkthrough

### One useId call, multiple derived IDs
```ts
const formId = useId();

const descriptionId = `${formId}-description`;
const amountId      = `${formId}-amount`;
const categoryId    = `${formId}-category`;
const typeId        = `${formId}-type`;
const datalistId    = `${formId}-categories`;
```
`useId()` is called once. All five IDs are derived from the single prefix with readable suffixes. If a second `AddTransactionForm` renders, it gets a different `formId` prefix — `":r1:"` instead of `":r0:"` — so all five derived IDs are automatically unique. The `datalistId` is separate from `categoryId`: the label links to the input via `categoryId`, and the input links to its autocomplete suggestions via `datalistId`. Two independent ID relationships on the same element.

### Label + input pairing
```tsx
<div className="flex flex-col gap-1">
  <label htmlFor={descriptionId} className="text-xs font-medium text-gray-500 dark:text-gray-400">
    Description
  </label>
  <input
    id={descriptionId}
    type="text"
    value={description}
    onChange={(e) => setDescription(e.target.value)}
    className={inputClass}
  />
</div>
```
The wrapping `div` with `flex flex-col gap-1` stacks label and input vertically with 4px gap. `htmlFor={descriptionId}` on the label and `id={descriptionId}` on the input are the link — same variable, guaranteed to match. The `placeholder` is removed: with a visible label, placeholder text is redundant and can be confusing when both are present.

### Shared style constants
```ts
const labelClass = 'text-xs font-medium text-gray-500 dark:text-gray-400';
const inputClass  = 'rounded-lg border ...';
```
All four labels share `labelClass`, all four inputs share `inputClass`. This is a local refactor to the component — not a global shared constant, just deduplication within the file. If one style needs to change, it changes in one place.

### The datalist — two IDs on one input
```tsx
<input
  id={categoryId}
  list={datalistId}
  ...
/>
<datalist id={datalistId}>
  {categories.map((c) => <option key={c} value={c} />)}
</datalist>
```
`id={categoryId}` is for the `<label htmlFor={categoryId}>` link. `list={datalistId}` is for the `<datalist id={datalistId}>` autocomplete link. Both are now generated (no hardcoded strings), so they're collision-safe even if two forms coexist on the same page.

## What to Remember

- `useId()` returns a stable, unique string per component instance — call it once per component, derive field IDs as `${formId}-fieldname`.
- `htmlFor` in JSX = `for` in HTML — they're renamed because `for` is a reserved keyword in JavaScript.
- Always pair `htmlFor` on the label with a matching `id` on the input — without this, clicking the label does nothing and screen readers can't associate the field with its label.
- Never generate IDs with `Math.random()` or `crypto.randomUUID()` in render — they change every render and break the link.
- `placeholder` is not a substitute for a label — it disappears when the user types and isn't reliably read by screen readers.
